1. Attempting to install LineageOS 18.1 on a Lenovo Tab 4 8 LTE (TB-8504X): work log, diagnostics and identified problems

Work dates: 10–12 November 2026

Device: Lenovo Tab 4 8 LTE, model TB-8504X, codename TB8504

Original OS: Android 8.1.0

Target OS: LineageOS 18.1 (Android 11), unofficial build

1.1. Preparation

1.1.1. Project goal

The goal was to replace the stock Android 8.1 with a more modern and lightweight operating system without Google services.

LineageOS 18.1 based on Android 11 was chosen as the target system. Installing Google Apps (GApps) was not planned from the outset.

Before modifying the system, it was decided to create a backup of the internal storage, verify firmware compatibility, and use a temporary TWRP boot without installing a custom recovery into the device's permanent partition.

1.1.5. Creating a backup

Before the installation attempts, a full block-level copy of the internal storage was created on the computer.

File:

~/Desktop/TB8504X_Backup/mmcblk0.img

The copy was performed via ADB:

adb exec-out "dd if=/dev/block/mmcblk0 bs=4M" | pv -s 15634268160 > ~/Desktop/TB8504X_Backup/mmcblk0.img

Size of the source block device and the resulting file:

15,634,268,160 bytes

After copying, it turned out that 93 extra bytes of dd text statistics output had ended up at the end of the file. The file size was corrected to the size of the source device:

truncate -s 15634268160 ~/Desktop/TB8504X_Backup/mmcblk0.img

Using fdisk, the presence of a GPT and 49 partitions was confirmed.

Backup limitation: a byte-for-byte comparison of the image with the source storage was not performed. Therefore, the existence of a full copy file is confirmed, but its absolute byte-for-byte accuracy has not been established. The image should not be considered a verified recovery method without additional checks.

The backup file contains not only user data but also system partitions, boot data and modem-related partitions. It cannot be blindly written back to the device as a whole: restoring a full image requires a separate assessment of the storage state and an understanding of the consequences.

1.2. Failed flashing attempt

1.2.1. First installation attempts and installer hang

The first installation was performed from a ZIP archive on a microSD card. An attempt to install via ADB sideload was also made.

In both cases, the process did not reach completion. The installer stopped at the stage:

Patching system image unconditionally...

The installation log contained the following messages:

block_image_update("/dev/block/bootdevice/by-name/system", ...)
Patching system image unconditionally...
performing update
blockimg version is 4
maximum stash entries 0
Patching system image unconditionally...
using existing stash /cache/recovery/2bdde8504898ccfcd2c59f20bb8c9c25f73bb524
Skipping already executed command: 0, last executed command for previous update: 0
writing 1024 blocks of new data

Installation progress stopped. The progress bar in TWRP did not move, and the last line of the log remained unchanged.

It was first necessary to establish whether the installer was actually performing a long operation or had hung completely. For this purpose, the state of the process, its system counters and the block device statistics were checked.

1.2.2. Checking the updater process

The installer process was found via:

adb shell 'ps -A | grep -iE "updater|update-binary|recovery" | grep -v grep'

Result:

root  338  1   ...  poll_schedule_timeout ... S recovery
root  377  338 ...  mtp_read              ... S recovery
root  994  338 ...  wait_on_page_bit      ... D updater

The updater process was in state D — uninterruptible waiting for an I/O operation. The wait channel displayed was wait_on_page_bit.

Additional check:

adb shell 'cat /proc/994/io; echo "--- WAIT CHANNEL ---"; cat /proc/994/wchan; echo "--- OPEN FILES ---"; ls -l /proc/994/fd'

Obtained counters:

rchar: 67815
wchar: 4201133
syscr: 29
syscw: 167
read_bytes: 569344
write_bytes: 4194304
cancelled_write_bytes: 0

Wait channel:

wait_on_page_bit

Among the open files, the following descriptor was found:

4 -> /dev/block/mmcblk0p25

This confirms that the installer process was directly working with the system partition of the internal storage.

The value write_bytes: 4194304 indicates 4 MiB of writes accounted for by the process. It does not prove that all of this data was successfully written to the physical medium.

1.2.3. Attempt to terminate the hung process

An attempt was made to gracefully terminate the installer:

adb shell 'kill -TERM 994; echo "SIGTERM sent"'

The command reported that the signal was sent, but the process remained in state D:

adb shell 'ps -A | grep updater | grep -v grep'

root  994  338  ...  wait_on_page_bit  ...  D updater

Processes in uninterruptible I/O wait cannot handle a termination signal while the kernel is waiting for the corresponding operation to complete. Therefore, repeated attempts to send signals do not eliminate the root cause of the hang.

A similar situation had been observed earlier during file system diagnostics: e2fsck processes also hung in state D.

The author does not see the point in describing the lengthy diagnostic process, as this would stretch out the article and reduce its suitability for analysis. It is more appropriate to move on to describing the successful solution to the problem.

1.3. Successful reflashing of the Lenovo Tab 4 8 (TB-8504) tablet to LineageOS 18.1

Date performed: 12.11.2026

Device: Lenovo Tab 4 8 (model TB-8504, Qualcomm Snapdragon 425 chipset, 2 GB RAM)

Installed OS: LineageOS 18.1 (Android 11) — build lineage-18.1-20230227-UNOFFICIAL-TB8504.zip

Host system (PC): Kali Linux (x86_64)

Final status: Successful. The system has booted and is functioning normally.

1.3.1. Problem description (symptoms)

When attempting a standard installation of the custom firmware via the custom recovery TWRP, the process hung completely at the stage "Patching system image unconditionally..." (the progress indicator did not move for more than 30 minutes).

  • The hang occurred both when installing via cable (adb sideload) and when installing locally from a physical MicroSD card.
  • The checksums of the firmware archive matched the original, which ruled out file corruption.

Technical cause of the failure:

On devices with a small amount of RAM (2 GB), when unpacking a heavy system.new.dat.br image (Brotli compression) inside the TWRP environment, an out-of-memory (OOM) condition occurs or a conflict arises when mounting the /system_root partition (error: Failed to mount '/system_root' (Invalid argument)). As a result, the built-in TWRP decoder enters an infinite loop.

↑ Back to contents

1.3.2. Adopted solution

A complete abandonment of unpacking and installing the firmware by means of TWRP. Instead:

  1. The firmware archive was unpacked and converted into a raw disk image (system.img) on the PC side under Kali Linux.
  2. The ready-made kernel (boot.img) and system (system.img) images were written directly into the tablet's internal flash memory (eMMC) partitions via the low-level Fastboot protocol.

↑ Back to contents

1.3.3. Step-by-step procedure

Stage 1. Unpacking the firmware archive on the PC

A working directory was created and the contents of the ZIP archive were extracted:

mkdir -p ~/rom && cd ~/rom
unzip /home/user/Downloads/lineage-18.1-20230227-UNOFFICIAL-TB8504.zip

Result: The key files boot.img, system.new.dat.br and system.transfer.list were extracted (there is no separate vendor partition in this build).

Stage 2. Decompression and assembly of the system.img image

1. The brotli archiver was installed and the system container was unpacked:

sudo apt update && sudo apt install -y brotli python3
brotli --decompress system.new.dat.br -o system.new.dat

2. A Python script, sdat2img.py, was created locally to convert the binary transfer list (system.transfer.list) and data (system.new.dat) into a mountable partition image:

python3 sdat2img.py system.transfer.list system.new.dat system.img

Script code sdat2img.py (Python):

        

import sys, os, struct

def rangeset(src):
    src_set = src.split(',')
    num_set = [int(item) for item in src_set]
    if len(num_set) != num_set[0] + 1:
        raise ValueError(f'Error parsing data: {src}')
    return [(num_set[i], num_set[i+1]) for i in range(1, len(num_set), 2)]

def parse_transfer_list_file(path):
    with open(path, 'r') as trans_list:
        version = int(trans_list.readline())
        new_blocks = int(trans_list.readline())
        if version >= 2:
            trans_list.readline()
            trans_list.readline()
        commands = []
        for line in trans_list:
            line = line.split(' ')
            cmd = line[0]
            if cmd in ['erase', 'new', 'zero']:
                commands.append([cmd, rangeset(line[1])])
        return version, new_blocks, commands

def main(TRANSFER_LIST_FILE, NEW_DATA_FILE, OUTPUT_IMAGE_FILE):
    BLOCK_SIZE = 4096
    version, new_blocks, commands = parse_transfer_list_file(TRANSFER_LIST_FILE)
    with open(OUTPUT_IMAGE_FILE, 'wb') as output_img, open(NEW_DATA_FILE, 'rb') as new_data_file:
        all_block_sets = [i for command in commands for i in command[1]]
        max_file_size = max(pair[1] for pair in all_block_sets) * BLOCK_SIZE
        for command in commands:
            if command[0] == 'new':
                for block in command[1]:
                    begin, end = block[0], block[1]
                    block_count = end - begin
                    output_img.seek(begin * BLOCK_SIZE)
                    while block_count > 0:
                        output_img.write(new_data_file.read(BLOCK_SIZE))
                        block_count -= 1
        if output_img.tell() < max_file_size:
            output_img.truncate(max_file_size)
    print(f'Done! Output image: {os.path.realpath(OUTPUT_IMAGE_FILE)}')

if __name__ == '__main__':
    main(sys.argv[1], sys.argv[2], sys.argv[3])

Result: A ready-made image /home/user/rom/system.img was produced.

Stage 3. Putting the device into Fastboot mode

  1. The tablet was forcibly powered off by long-pressing the power button (15 seconds).
  2. The key combination Volume Down + Power was held until the Fastboot mode screen appeared.
  3. The connection to the PC was checked:
fastboot devices

Output: HGAGWPMF fastboot

Stage 4. Wiping partitions and directly writing the images

  1. The old kernel and system partitions were erased:
fastboot erase boot
fastboot erase system
  1. The new kernel was flashed:
fastboot flash boot boot.img
  1. The system partition was flashed (the utility automatically split the image into 4 sparse segments, with a total write time of ~311 seconds):
fastboot flash system system.img

Stage 5. Resetting user data and booting

Note: The standard command "fastboot -w" failed with the error "mke2fs failed with status 1" (a peculiarity of the platform-tools build in Kali Linux). The problem was solved by directly wiping the partitions, after which the new OS initialized the ext4 file system itself on first boot:

fastboot erase userdata
fastboot erase cache
fastboot reboot

Result: The tablet rebooted successfully, passed the initial LineageOS initialization stage and reached the welcome screen.

Stage 6. Performance check

The performance of LineageOS 18.1 was checked — the system works correctly. The F-Droid application was downloaded from the official website, through which the necessary applications were installed, including Aurora Store. In turn, Aurora Store was used to install applications that are absent from the F-Droid repository.

As a result, the check showed that the build lineage-18.1-20230227-UNOFFICIAL-TB8504, based on Android 11, works no worse, and in many respects even better, than the factory Android 8 OS.

Installing LineageOS 18.1 without Google services and other additional services (which the author does not consider useful or necessary for himself) led to a significant improvement in the quality of the tablet's OS performance.

It became possible to install Proton services, as well as some other services incompatible with Android 8.

After two weeks of testing — active work with the browser version of DeepSeek, watching media files in the VLC player, typing in Quick Edit and solving other standard tasks — no crashes or hangs were detected. The only exception was some applications refusing to work because they could not detect Google services.

1.3.4. Conclusions and recommendations for the future

For devices of the Lenovo Tab 4 series (TB-8504), when installing custom Android 10/11 firmware, the direct flashing method via fastboot flash is the most stable and safe.

2. Upgrade of a system unit built on the BIOSTAR N68S3B motherboard

To improve the performance of the old system unit, it was decided to upgrade it.

The main goal of the upgrade was to squeeze the maximum possible out of the old platform.

Originally, the system unit was assembled in a base (budget) configuration to reduce the final retail price. However, the BIOSTAR N68S3B motherboard itself is built on durable solid capacitors and has remained fully functional, so it was decided to replace the entry-level components with top-tier ones (new or used) from among those supported, in order to fully unlock its potential.

Brief specifications of the BIOSTAR N68S3B motherboard

🔧 Key parameters

  • Socket: AM3
  • Chipset: NVIDIA MCP68S / GeForce 7025
  • Form factor: Micro ATX (235 mm × 170 mm)
  • CPU support: AMD Phenom II / Athlon II / Sempron
  • Max CPU TDP: 95 W

💾 Memory and graphics

  • Memory slots: 2 × DDR3 DIMM (dual-channel mode)
  • Max memory capacity: 8 GB
  • Integrated graphics: NVIDIA GeForce 7025 (up to 512 MB shared memory)

🔌 Expansion slots and storage

  • PCIe: 1 × PCIe x16
  • PCI: 1 × PCI
  • SATA: 2 × SATA II (3 Gbit/s), RAID 0/1 support
  • IDE: 1 connector

🌐 Network, audio and ports

  • Network: Realtek RTL8201CL (10/100 Mbit/s)
  • Audio: VIA VT1708B (6-channel HD audio)
  • USB: 4 USB 2.0 ports on the rear panel + 2 internal headers (4 more ports)
  • Video output: 1 × VGA

The 2 GB memory module that was installed in the system unit at purchase was replaced with two Hyundai HMT351U6CFR8C-PB modules of 4 GB each.

This was not difficult: all that was needed was to release the latch, remove the old memory module and install the two new ones, pressing on them gently and carefully until the slot latches clicked into place.

A case fan, the Arctic P9 Silent, was installed in the system unit to improve air circulation and ventilation of all case components. At purchase, the power supply came without a case fan. But since it was decided to install a more powerful processor, it was also decided to install a case fan to improve overall case cooling.

Next, the Athlon II X2 220 processor installed at purchase was replaced with an AMD Athlon II X4 645 processor.

Advantages of the new Athlon II X4 645 processor over the old Athlon II X2 220:

📊 Key differences in numbers

Parameter Old Athlon II X2 220 New Athlon II X4 645
Cores / Threads 2 / 2 4 / 4
Base clock 2.8 GHz 3.1 GHz (+0.3 GHz)
TDP (thermal design power) 65 W 95 W (higher, but the cooler handles it)
L2 cache 2 × 512 KB 4 × 512 KB (twice as much)

That is, even a morally outdated system unit, having received such a processor, will perform significantly better.

The BIOSTAR N68S3B motherboard is incompatible with processors with a TDP above 95 W, so the Athlon II X4 645 was chosen specifically — a processor of the same series as the old one and fully compatible with this motherboard.

Also, whereas previously, with the old processor, the memory modules ran at an effective frequency of 533 MT/s despite being capable of 667 MT/s, after installing the new processor the memory modules rated for 667 MT/s are no longer limited by the old processor's inability to support a higher frequency. The new Athlon II X4 645 allows the memory modules to run at their rated 667 MT/s.

An important point: when removing the old processor, the socket retention lever (the ZIF mechanism), after leaving the retaining notch in the horizontal position, did not rise to the standard 90 degrees relative to the motherboard plane. Due to long-term use without replacement — the processor had been in the socket for 14 years (from 2012 to 2026) — the mechanism had seized: the lever stopped in the 70–80 degree range.

To avoid breaking the plastic socket body and bending the processor pins, brute force was not used. Instead, the mechanism was carefully worked loose with a series of light rocking movements of the lever within the 70–90 degree working range, with a smooth increase in force. At about the tenth repetition, the internal latch released, and the lever moved freely to a strictly vertical position (90 degrees). The old processor was removed without resistance, the new one was installed (aligning the keys on the package and the socket) and secured by smoothly returning the lever to its original notch.

Since processors for this socket were discontinued long ago, the chip was purchased on the secondary market from a specialized store after pre-sale testing (buying such components privately from individuals without testing is strongly discouraged). At the same time, the CPU cooler and case fan were installed exclusively new and with a reliable design.. Skimping on the cooling system is unacceptable: effective heat dissipation is critical, since the stability and service life of all system unit components depend directly on the temperature regime.

The CPU cooler chosen was the CIA-123W2C model (4-pin PWM, 2 copper heat pipes, 123 mm fan).

Before choosing the cooler, the space inside the system unit was carefully measured and compared with the cooler's dimensions. It was established that the cooler would fit in the required position without touching other parts of the system unit and without obstructing the routing of various cables, with clearances of 6–7 millimetres and more, sufficient for safe and reliable operation.

Advantages of this cooler: a 4-pin (4-pin PWM) cooler, unlike the 3-pin stock cooler installed at purchase with the system case, will perform much better, since its fan speed will be regulated by the motherboard via PWM, unlike the old 3-pin one, which runs constantly at maximum speed and creates noise even when the PC is idle and the processor is loaded at 2–3%. Also, the new cooler has a much larger fan diameter, which allows it to achieve the necessary cooling effect at a lower rotational speed. In addition, the new cooler is designed to dissipate heat from processors with a TDP of up to 110 W, while the new Athlon II X4 645 processor has a TDP of 95 W, meaning the cooler has a power headroom of about 15%, which guarantees reliable processor cooling. And overall, the copper-aluminium heatsink of the chosen cooler with copper heat pipes performs more efficiently than an aluminium heatsink.

It was decided to forgo a cheaper cooler of the classic design with radially arranged fins (the so-called "sunflower" type) for several reasons. Firstly, due to the dense layout of components on the motherboard, there could be difficulties with its dimensional compatibility. Secondly, the heatsinks of most budget models of this form factor are a solid aluminium profile without a copper core or heat pipes. Thirdly, such coolers are usually equipped with a 3-pin connector without PWM speed control support: due to the absence of a 4-pin connector, the fan runs constantly at maximum speed, which leads to increased noise levels even at idle.

During installation, the fan was first removed from the cooler heatsink to make it easier to handle the heatsink by hand and to avoid damaging the fan when securing the heatsink mounts.

Next, a test fit was performed: the heatsink was placed in the required position on the processor without securing. As a result, it was decided to remove the power supply from the case for more convenient heatsink installation.

The most important thing: the BIOSTAR N68S3B motherboard has a specific AMD cooler mounting frame (a "retention bracket") with a lower position of the hooks for engaging the cooler clips than the universal round frame supplied with the cooler. Due to the specific layout of the motherboard, it was not possible to replace the stock retention bracket with the universal one — the round base would simply have run into the capacitors and memory modules.

During the preliminary installation of the cooler, it turned out that the retention clip had excessive stiffness: even with considerable force, its eyelets did not reach the tabs (teeth) of the stock mounting frame. Further increases in pressure could have led to deformation or breakage of the heatsink, chipping of the processor die, as well as damage to the socket and the motherboard PCB.

To avoid damage, installation was paused to adjust the retention mechanism. The clip was carefully bent open and released in several stages, gradually reducing its stiffness. The goal was to achieve a compromise: reduce the compression range to a level allowing the eyelets to engage the mounting frame, while still maintaining strong retention necessary for tight contact between the heatsink base and the processor heat spreader.

After a series of test fits and adjustments, the clip engaged the mounting slots with noticeable but safe force. Thermal interface GD900 was applied to the processor heat spreader and the cooler was secured. The heatsink fan was positioned to blow towards the rear case fan. This scheme creates a single through airflow that effectively exhausts hot air from the system unit and improves overall cooling of the components.

Recommendation: it is better to buy a small syringe of thermal paste separately, since the thermal paste supplied with the cooler may not be enough, especially if the first attempt to install the heatsink is unsuccessful and you have to wipe off the thermal paste and reapply it, repeating the attempt.

Attention! If you need to loosen the heatsink retention clip, do so as carefully as possible. It is important to find the balance: the clip eyelets must reach the tabs (teeth) of the mounting frame, but the clip itself must retain sufficient stiffness for tight pressure of the cooler base against the processor heat spreader. When using the supplied universal adapter ring, the clip will most likely latch in place as intended. Do not bend it open unless absolutely necessary.

Next, the 4-pin connector was cleaned of dust with a fine brush, since the fourth contact, not used by the 3-pin fan connector of the old cooler, was heavily dusted, which could have prevented correct connection of the connector. After that, the 4-pin fan plug of the new cooler was connected to the connector.

After that, the power supply was returned to its original position.

Next, the computer was started, and two 20-minute stress tests were performed: first at medium load, then at maximum. The tests showed high-quality processor cooling.

As the software platform, the latest version of the Kali Linux distribution with all the latest updates and the lightweight XFCE desktop environment was installed on the upgraded PC. To visually verify the correct detection of components, the amount of RAM and the temperature regime, the final configuration was output in the terminal using the inxi -Fxzs utility:

  • Operating system: Kali GNU/Linux 2026.3 (kali-rolling), kernel Linux 7.1.5+kali-amd64 (x86_64)
  • Desktop environment: Xfce 4.20.2 (X.Org 21.1.24)
